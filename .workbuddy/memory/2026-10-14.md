  从外往里逐层排除。配套"三条 curl 定层法"（直连4001 / 走Nginx / 走域名，三种结果组合直接锁定故障层）
- 内容组织：第0章五条铁律（先救火再定位、重启前存现场、一次只改一个变量、
  改动前备份、记录时间戳）→ 第2章一键现场采集脚本 → 第3章 11 个场景化排查手册
  → 第5章 3 个完整案例（502端口写错 / 磁盘满inode耗尽 / 磁盘满+OOM导致重启循环）
  → 第6章应急vs根因时间线 → 第7章故障报告模板 → 第8章预防性checklist
- 三个关键洞察（已内化为方法论）：
  1. `code=exited` vs `code=killed` 是排查分水岭：前者看应用日志，后者查 OOM/cgroup/外部干预
  2.502/504 的答案 90% 直接写在 nginx error.log 里，不必猜
  3. 要在 nginx 里配 `$request_time` / `$upstream_response_time` 才能秒级区分"慢在Nginx"还是"慢在后端"
- 产出2：`I:/练习/nginx/deploy/lab-troubleshoot.sh`（约 930 行），8 个可注入故障的演练脚本：
  502 / disk / oom / port / badconf / perm / restart-loop / timeout，
  每个场景都配套`answer <场景>` 给出完整排查路径与参考答案，支持 `restore` 一键还原
- 脚本设计上的关键修正：
  - 磁盘注入用 `fallocate`（真实分配块）而非 `truncate`（只建稀疏文件不占空间），并加安全阀（可用空间<6G 拒绝默认注入）
  - 内存注入必须真实持内存（python bytearray 逐页写入 / node Buffer.alloc），
    原写法 `dd of=/dev/null` 不占内存等于没注入
  - perm 场景记录原权限到 `.lab-state.perm`，还原时精确恢复而非粗暴 chmod 644
  - 所有注入前 `do_backup` 备份 nginx.conf/站点配置/systemd unit

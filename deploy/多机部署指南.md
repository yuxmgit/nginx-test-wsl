# 多机部署指南：用当前 Jenkins 把项目部署到另一台 Ubuntu

> 适用场景：Jenkins 跑在 WSL Ubuntu（控制面），业务要部署到另一台物理/虚拟 Ubuntu 服务器（执行面）。
>
> 前置：本项目的单机 CI/CD 流程已跑通（见 `CI-CD部署指南.md`）。

---

## 0. 先看清一个决定性的约束

你的 Jenkins 在 **WSL** 里，WSL 是 NAT 网络：

```
Windows 主机
  └── WSL Ubuntu (Jenkins)     172.18.32.10   ← NAT 内网地址
        │
        │  能出站 → 目标机 ✅
        ← 能被目标机主动连回来？ ❌（NAT 后面，没有公网入口）
```

所以三种经典分发方式里：

| 方式 | 目标机要能访问 GitHub 吗 | 目标机要能访问 Jenkins 吗 | 结论 |
|---|---|---|---|
| **Push**（Jenkins 主动 SSH 推） | 否 | **否**（Jenkins 主动出站） | ✅ **本方案采用** |
| Pull（目标机自己 git clone） | 是 | 否 | 需给每台目标机配 GitHub 凭据，且目标机必须能出网 |
| Pull via Webhook | 是 | 是（需隧道/公网） | ❌ WSL NAT 下不可行 |

**一句话结论：Jenkins 主动 SSH 推送到目标机，是当前架构下唯一不需要额外网络改造的方案。**

本方案新增 3 个文件：

| 文件 | 位置 | 作用 |
|---|---|---|
| `deploy/target-prepare.sh` | **目标机** | 一次性准备：装依赖、建用户/目录、生成 systemd unit、nginx 配置、受限 sudo |
| `deploy/remote-deploy.sh` | **Jenkins 侧** | 多机部署执行：备份 → rsync → 重启 → 健康检查 → 失败回滚 |
| `deploy/inventory.ini` | **仓库**（从 `.example` 复制） | 主机清单：每台机器一段配置 |
| `Jenkinsfile` | **仓库**（已改） | 新增 `REMOTE_DEPLOY` / `TARGET_HOSTS` / `DRY_RUN` 三个参数 + 多机分支 |

## 1. 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│  控制面（WSL Ubuntu）                                        │
│                                                              │
│  GitHub ──push──► Jenkins（Poll SCM / Webhook）              │
│                       │                                      │
│                       ▼ 阶段4：生成 version.json              │
│                       ▼                                      │
│                 deploy/remote-deploy.sh                      │
│                       │  读 deploy/inventory.ini             │
│                       │  rsync over SSH（带 deploy_key）      │
└───────────────────────┼──────────────────────────────────────┘
                        │ SSH 22 出站
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   ┌─────────┐     ┌─────────┐     ┌─────────┐
   │ web-01  │     │ web-02  │     │ web-03  │   目标机（Ubuntu）
   │ 192.168 │     │ ...     │     │ ...     │
   │         │     │         │     │         │
   │ nginx:80│     │         │     │         │
   │  ├4001  │     │         │     │         │
   │  └4002  │     │         │     │         │
   └─────────┘     └─────────┘     └─────────┘
        每台独立：备份→同步→重启→健康检查→失败自回滚
```

**注意架构上的一个重要区分**：

- 本方案是「**每台机器完整复制**」（role=full）——每台都有 nginx + 4001 + 4002，自成闭环，最容易跑通。
- 如果要做「web 入口机 + app 后端机」分离，`role` 参数已预留 `web` / `app`，但 **upstream 必须改成远端 IP**（见第 6 章）。

## 2. 第一步：准备目标机（一次性，在目标机上做）

### 2.1 目标机基础要求

| 项 | 要求 |
|---|---|
| 系统 | Ubuntu 20.04+ / Debian 11+ |
| systemd | 必须启用（`ps -p 1 -o comm=` 应输出 `systemd`） |
| 网络 | 能被 WSL 所在网络访问 22 端口；能出站到 WSL（双向） |
| 免密 | 目标机 **不要求** 免密 sshd 进来，Jenkins 主动连出去即可 |

### 2.2 用 target-prepare.sh 一键准备

把项目拉到目标机（先 `git clone` 或 scp 过去），然后：

```bash
# 在目标机上，以 root 运行
sudo bash deploy/target-prepare.sh \
    --deploy-dir /srv/nginx-project \
    --run-user   appuser \
    --ssh-user   deploy \
    --role       full \
    --upstream   127.0.0.1:4001,127.0.0.1:4002
```

脚本会做这些事（幂等，可重复执行）：

| 步骤 | 动作 |
|---|---|
| 1 | 装 nginx / rsync / acl / curl / Node.js |
| 2 | 建 `deploy`（登录用）与 `appuser`（跑服务用）两个用户——**职责分离** |
| 3 | 建 `/srv/nginx-project`，ACL 授权：deploy 可写、appuser 可读 |
| 4 | 生成 `api-server1.service` / `api-server2.service`（`User=appuser`，`WorkingDirectory=/srv/nginx-project/backend`） |
| 5 | 写 `/etc/nginx/conf.d/api-upstream.conf`（upstream 块）+ 站点配置，重启 nginx |
| 6 | 写受限 sudo 白名单 `/etc/sudoers.d/deploy-nginx-app`，`visudo -c` 校验 |
| 7 | 打印接下来要在 Jenkins 侧做的三件事 |

> **为什么登录用户和运行用户要分开？**
> `deploy` 需要可写部署目录（rsync 要写），`appuser` 只需要可读代码。
> 如果用同一个用户，Jenkins 一旦被入侵就能改服务代码。分开后，Jenkins 凭据泄露 ≠ 服务被完全控制。

### 2.3 验证目标机自己部署是通的（**必做**）

在目标机上先手工跑一次，确认环境本身没问题：

```bash
sudo systemctl status api-server1 api-server2 nginx
curl -s http://127.0.0.1:4001/api/user
curl -s http://127.0.0.1:4002/api/user
curl -s http://127.0.0.1/api/user     # 经 nginx
```

**这一步不通过就别往下走**，否则后面出问题分不清是环境问题还是 SSH 链路问题。

## 3. 第二步：打通 SSH 链路

### 3.1 在 Jenkins 机器（WSL）上生成专用部署密钥

```bash
# 注意：不要复用 GitHub 那把 key，职责分开
sudo install -d -m 700 -o jenkins -g jenkins /var/lib/jenkins/.ssh
sudo -u jenkins ssh-keygen -t ed25519 -N '' -f /var/lib/jenkins/.ssh/deploy_key
```

> 若 `jenkins` 用户不能 `ssh-keygen`，用root 生成再改属主：
> ```bash
> sudo ssh-keygen -t ed25519 -N '' -f /var/lib/jenkins/.ssh/deploy_key
> sudo chown jenkins:jenkins /var/lib/jenkins/.ssh/deploy_key*
> sudo chmod 600 /var/lib/jenkins/.ssh/deploy_key
> ```

### 3.2 把公钥授权给目标机

在目标机上（root）：

```bash
sudo install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
sudo tee /home/deploy/.ssh/authorized_keys > /dev/null
# 把 deploy_key.pub 的内容粘贴进来，然后：
sudo chmod 600 /home/deploy/.ssh/authorized_keys
sudo chown deploy:deploy /home/deploy/.ssh/authorized_keys
```

### 3.3 在 WSL 上测连通

```bash
sudo -u jenkins ssh -i /var/lib/jenkins/.ssh/deploy_key \
    -o StrictHostKeyChecking=no deploy@192.168.1.101 "hostname; whoami"
```

**必须能免密登录**。若提示 `Permission denied (publickey)`，检查：
- 私钥权限是否 600、属主是否 jenkins
- `authorized_keys` 是否 600、属主是否 deploy
- `deploy` 用户的 shell 是否被设成 `/usr/sbin/nologin`

## 4. 第三步：写主机清单 inventory.ini

```bash
cp deploy/inventory.ini.example deploy/inventory.ini
```

```ini
[web-01]
host        = 192.168.1.101
ssh_user    = deploy
deploy_dir  = /srv/nginx-project
run_user    = appuser
role        = full
health_port = 80
enabled     = true

[web-02]
host        = 192.168.1.102
ssh_user    = deploy
deploy_dir  = /srv/nginx-project
run_user    = appuser
role        = full
health_port = 80
enabled     = true
```

字段含义：

| 字段 | 必填 | 说明 |
|---|---|---|
| `host` | ✅ | IP 或域名，**Jenkins 必须能 SSH 直连** |
| `ssh_user` | ✅ | 远程登录用户（一般是 `deploy`） |
| `deploy_dir` | ✅ | 代码落地目录，**必须与目标机 systemd 的 `WorkingDirectory` 一致**（脚本会校验） |
| `run_user` | ✅ | 服务运行用户 |
| `role` | — | `full`（默认，nginx+双后端）/ `web`（仅前端+nginx）/ `app`（仅后端） |
| `upstream` | — | web 角色的后端地址，逗号分隔。留空 = `127.0.0.1:4001,127.0.0.1:4002` |
| `health_port` | — | 健康检查访问 nginx 的端口，默认 80 |
| `enabled` | — | `false` 可临时摘掉某台机器（灰度/维护） |

> ⚠️ `inventory.ini` **建议入库**（主机清单是部署配置的一部分，团队共享），但里面只有主机地址没有密钥，安全上没问题。若你的规范要求敏感配置外置，也可 `.gitignore` 掉它，改用 `INVENTORY_FILE` 环境变量指向外部路径。

## 5. 第四步：在 Jenkins 里跑起来

### 5.1 参数说明

改造后的 `Jenkinsfile` 新增了 3 个构建参数：

| 参数 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `REMOTE_DEPLOY` | boolean | `false` | `false`=本机部署（原逻辑，完全不受影响）；`true`=多机远程部署 |
| `TARGET_HOSTS` | string | `''` | 指定主机 ID，逗号分隔；留空 = inventory 中全部 enabled 的机器 |
| `DRY_RUN` | boolean | `false` | 演练模式：只打印执行计划，不真正部署 |

### 5.2 首次建议先演练

```
构建 → 勾选 REMOTE_DEPLOY 和 DRY_RUN → 构建
```

日志会打印每台机器将要执行的动作，但不动任何文件。确认主机清单解析正确后再取消 DRY_RUN。

### 5.3 正式部署

```
构建 → 勾选 REMOTE_DEPLOY（不勾 DRY_RUN）→ 构建
```

流水线行为：

```
阶段1 拉取代码
阶段2 环境检查
阶段3 部署前检查        ← Node 语法检查、文件存在性
阶段4 生成版本信息      ← version.json（每个目标机版本号一致）
阶段5 执行部署          ← remote-deploy.sh：逐台 备份→rsync→重启→健康检查→回滚
阶段6 冒烟测试          ← 每台目标机独立成一个 stage，含前后端版本一致性校验
```

失败时 `post { failure }` 会自动 SSH 到每台目标机拉取 `journalctl` 与 nginx error log。

### 5.4 命令行等价操作（排障用）

```bash
# 在 Jenkins 容器/WSL 上
sudo -u jenkins bash deploy/remote-deploy.sh \
    /var/lib/jenkins/workspace/nginx-deploy \
    deploy/inventory.ini \
    web-01 --dry-run

# 只部署一台
sudo -u jenkins bash deploy/remote-deploy.sh \
    /var/lib/jenkins/workspace/nginx-deploy \
    deploy/inventory.ini web-01
```

## 6. 角色分离进阶：web 入口机 + app 后端机

如果后端要跑在多台机器上、前端入口单独一台，`upstream` 就不能写 `127.0.0.1` 了。

### 6.1 后端机（role=app）

```bash
sudo bash deploy/target-prepare.sh --role app --upstream 127.0.0.1:4001,127.0.0.1:4002
```

inventory：

```ini
[app-01]
host       = 192.168.1.201
ssh_user   = deploy
deploy_dir = /srv/nginx-project
run_user   = appuser
role       = app
enabled    = true
```

### 6.2 入口机（role=web），upstream 指向后端机真实 IP

```bash
sudo bash deploy/target-prepare.sh \
    --role web \
    --upstream 192.168.1.201:4001,192.168.1.202:4001
```

inventory：

```ini
[web-01]
host        = 192.168.1.101
ssh_user    = deploy
deploy_dir  = /srv/nginx-project
run_user    = appuser
role        = web
upstream    = 192.168.1.201:4001,192.168.1.202:4001
health_port = 80
enabled     = true
```

### 6.3 三个必须注意的点

1. **健康检查位置变了**。`role=web` 时只检查 nginx（`/api/user` 经 upstream 转发），不检查 4001/4002 端口——那两个端口在后端机上。
2. **入口机的前端版本校验仍要能通过**。`/api/version` 是经 nginx → upstream → 后端机返回的，后端机上必须有同版本的 `version.json`。所以**后端机也必须部署**（`role=app` 也要同步 `frontend/version.json`）。
   > `remote-deploy.sh` 里 `role=app` 只同步 `backend/`，**不含** `frontend/`。如果需要后端机也提供 `/api/version`，需要额外同步 `frontend/version.json`。这是当前实现的一个已知限制，见第 8 章。
3. **端口要对外可达**。后端机的 4001/4002 需要放行防火墙，否则入口机转发会 502。

## 7. 失败处理机制

### 7.1 单机三层防线

| 防线 | 位置 | 触发条件 | 影响 |
|---|---|---|---|
| 部署前语法检查 | 阶段 3 | Node 语法错、文件缺失 | **零影响**，线上完全没动 |
| 健康检查 + 自动回滚 | 阶段 5 步骤 5 | 4001/4002/nginx 任一非 200（重试 10 次×2 秒） | 短暂抖动后恢复旧版 |
| 版本一致性校验 | 阶段 6 | 前端 `version.json` ≠ 后端 `/api/version` | 标记为可疑版本，需人工确认 |

### 7.2 多机部分失败

`remote-deploy.sh` 的行为是「**一台失败不影响其余**」：

```
web-01  ✅ 成功
web-02  ❌ 健康检查失败 → 自动回滚到该台的备份
web-03  ✅ 成功（仍然继续部署）
──────────────────────────────────────
汇总：成功 2 台 / 失败 1 台
最终：构建标记为失败，日志里列出失败主机
```

> 实现方式：`deploy_host` 在子 shell 中执行，内部的 `die` 只终止子 shell，主循环继续。
> 这一点很重要——如果一台机器磁盘满了导致失败，不该让剩下 9 台都停掉。

### 7.3 回滚位置

每台机器各自保留备份，路径：

```
/var/lib/deploy-backups/<主机ID>/<时间戳>/
```

保留策略与单机版一致（最近 5 份）。手动回滚：

```bash
ssh deploy@192.168.1.101
sudo rsync -rl --delete /var/lib/deploy-backups/web-01/20261023-163500/backend/ /srv/nginx-project/backend/
sudo rsync -rl --delete /var/lib/deploy-backups/web-01/20261023-163500/frontend/ /srv/nginx-project/frontend/
sudo systemctl restart api-server1 api-server2
sudo systemctl reload nginx
```

## 8. 已知限制与后续待办

| # | 限制 | 影响 | 建议 |
|---|---|---|---|
| 1 | `role=app` 只同步 `backend/`，不含 `frontend/version.json` | 后端机的 `/api/version` 会返回 `unknown`，导致入口机的版本一致性校验失败 | 角色分离场景下，让后端机也同步 `frontend/version.json`（可加 `role=app` 时同步单个文件的逻辑） |
| 2 | upstream 是**部署时固定**的，不随 inventory 变更自动改写 | 增删后端机需要手工改目标机 nginx 配置 | 可扩展为在 deploy 前推送 upstream 配置片段 |
| 3 | 部署是**串行**的（逐台 rsync + 重启 + 检查） | 10 台机器部署时间约 10×单台 | 可改 `xargs -P` 并行，或用 Ansible 的 `--forks` |
| 4 | 目标机时钟未同步 | 版本面板的 buildTime 是 Jenkins 侧生成的，不受影响；但 `date` 判断回滚目录时会错乱 | 目标机装 `chrony` 或 `systemd-timesyncd` |
| 5 | 没有蓝绿/滚动升级 | 部署期间该机短暂不可用 | 需要零停机时，用 nginx upstream 加 `down` + `backup` 标记逐台摘挂 |

## 10. 【实战】用 WSL 第二发行版模拟「另一台 Ubuntu 服务器」

> 场景：手边没有真正的服务器，但想完整跑通 Jenkins 多机部署链路。
> 做法：在 Windows 上再装一个 WSL 发行版（Ubuntu-24.04），当成远程目标机。

### 10.1 先理清一件事：ngrok 在这里没用上

你已经在跑 ngrok（`localhost:8080` → `https://xxx.ngrok-free.app`）。它的作用是：

```
GitHub --(webhook, 入站)--> ngrok --> localhost:8080 --> Jenkins
```

这是**入站**方向，给「push 后自动触发构建」用。

而多机部署是**出站**方向：

```
Jenkins --(SSH 主动连出去, 出站)--> 目标机
```

Jenkins 是客户端，**目标机不需要任何公网入口**。所以：

- ✅ 多机部署**不需要**给目标机开 ngrok 隧道
- ✅ 现有 ngrok 隧道**不受影响**，两者互不干扰
- ❌ 如果你想从**外部浏览器**访问「目标机」的网站，那才需要给目标机单独开隧道（见 10.6）

### 10.2 WSL 多发行版的三个真实坑

在动手前必须知道，否则会浪费大量时间：

| 坑 | 现象 | 解法 |
|---|---|---|
| **① 新发行版没开 systemd** | `systemctl` 命令不存在，或服务无法托管 | 在目标发行版的 `/etc/wsl.conf` 写 `[boot] systemd=true`，然后 `wsl --terminate` 重启该发行版 |
| **② 新发行版没装 sshd** | Jenkins SSH 报 `Connection refused` | 目标发行版装 `openssh-server` 并 `systemctl enable ssh` |
| **③ IP 每次都变** | inventory 里写死的 IP 今天能连、明天失效 | **绝不要写死 IP**。用 `host = wsl:Ubuntu-24.04`，部署时自动解析 |
| **④ 两发行版跨网段**（补充） | SSH 一直超时，ping 也不通 | 见下方 10.2.1，**统一 `networkingMode=nat`** |

> 坑 ③ 最坑。WSL2 是 NAT 网络，**每次 `wsl --shutdown` 或重启，发行版 IP 都会重新分配**。
> 如果你在 inventory 里写 `192.168.x.x`，今天能连上，重启电脑后 Jenkins 就直接部署失败了——而且报错是「SSH 不通」，很难联想到是 IP 变了。
>
> 所以本方案实现了 `wsl:<发行版名>` 语法：`remote-deploy.sh` 在部署前会调用
> `wsl.exe -d <发行版名> -- hostname -I` 拿到**当下真实 IP**。

#### 10.2.1 坑 ④：两个发行版不在同一网段（最容易卡住的一步）

**典型症状**：Ubuntu-24.04 装好后 `ip address` 显示 `10.10.10.2`，而 Jenkins 发行版显示 `172.18.32.10/20`。两者网段完全不同，Jenkins 去 ping 目标机直接超时。

**根因**：WSL 支持两种网络模式，不同发行版可能处于不同模式：

| 模式 | 发行版地址 | 表现 |
|---|---|---|
| `nat`（默认） | `172.18.x.x/20`（Hyper-V 虚拟网卡） | 同一 VM 内的发行版**可以互相直连** |
| `mirrored` | 直接用宿主机局域网 IP（如 `172.16.21.177`） | 也可直连，但**与 NAT 发行版跨网段隔离** |

混合模式下，NAT 发行版（`172.18.x`）无法主动访问 mirrored 发行版（`172.16.x` 或 `10.x`）——因为宿主机路由表里没有对应网段的路由，Windows 也到不了 `10.0.0.0/8`。

**解决：统一为 NAT 模式**

```bash
# 在任一 WSL 发行版内执行（脚本会自动处理 .wslconfig 的 BOM 与段落插入）
bash deploy/wsl-fix-networking.sh
```

然后**必须**在 Windows PowerShell 执行（这一步不能省，否则配置不生效）：

```powershell
wsl --shutdown
```

再验证两个发行版是否同网段：

```powershell
wsl -d Ubuntu -- ip -4 addr show eth0
wsl -d Ubuntu-24.04 -- ip -4 addr show eth0
```

两者都应是 `172.18.x.x` 开头。

> **为什么必须统一，不能靠别的办法绕过去？**
> 因为 Jenkins 需要主动 SSH 连目标机，这是「出站」方向。
> 跨网段时 WSL 的虚拟网卡之间没有路由，出站包根本到不了目标机。
> 统一网络模式是唯一干净的做法——它改的是 Windows 侧的 Hyper-V 虚拟网络配置，
> 对两个发行版都生效，且 `wsl --shutdown` 后立即可用。
>
> 另一条路是给目标机做 Windows 端口转发（`netsh interface portproxy`），
> 把 Windows 的某个端口映射到目标发行版的 22 端口，再让 Jenkins 连 Windows。
> 但这会让 inventory 里的 `host` 指向 Windows 而非目标机，语义混乱，
> 而且目标机重启后转发规则可能失效——**不推荐**。

### 10.3 第一步：安装第二发行版

在 **Windows PowerShell**（不是 WSL 内）执行：

```powershell
wsl --install -d Ubuntu-24.04
```

> 说明：
> - `wsl --list --online` 可查看所有可安装的发行版列表
> - 安装完成后**不要**急着进去配环境，直接用下面的脚本自动化
> - 首次进入会要求设置用户名密码，记住即可（脚本里用的是 root 权限）

验证：

```powershell
wsl -l -v
```

应该能看到 `Ubuntu` 和 `Ubuntu-24.04` 两个发行版都在 Running 状态。

> **如果新发行版的 IP 不是 `172.18.x.x`**（比如显示 `10.10.10.2` 或 `172.16.x.x`），
> 说明它和 Jenkins 发行版的网络模式不一致，**先做 10.2.1 的网络模式统一**，
> 否则后面 SSH 一定连不上。脚本 `wsl-second-node.sh` 会在步骤 0.5 检测并提示。

### 10.4 【推荐】一条命令走完全流程

> 这是最省事的做法。脚本是个**状态机**：你反复执行同一条命令，它自动判断进度、继续往下推。

```bash
# 在 Jenkins 所在的 WSL 发行版（Ubuntu）内执行
bash /tmp/wsl-setup-all.sh
```

它会依次完成 5 个阶段：

| 阶段 | 做什么 | 需要你做什么 |
|---|---|---|
| 1 | 改写 `.wslconfig`，写入 `networkingMode=nat` | 提示你执行 `wsl --shutdown` |
| 2 | 检查两个发行版是否同网段 | 执行完 shutdown 后重跑本脚本 |
| 3 | 目标发行版开 systemd、装 sshd、建密钥、跑 `target-prepare.sh` | 重跑本脚本 |
| 4 | 实测 SSH 免密，**自动写入 `deploy/inventory.ini`** | 重跑本脚本 |
| 5 | dry-run 试部署 | 完成 |

**唯一需要你手动做的**，是在阶段 1 之后，于 Windows PowerShell 执行：

```powershell
wsl --shutdown
```

（这会同时停掉 Jenkins，重进发行版后确认 `systemctl is-active jenkins` 为 active）

随时查看进度：

```bash
bash /tmp/wsl-setup-all.sh --status
```

> 脚本已放在 `//wsl$/Ubuntu/tmp/`，也就是你 WSL 里的 `/tmp/wsl-setup-all.sh`。
> 仓库里的源文件在 `deploy/wsl-setup-all.sh`（也有 `wsl-net-probe.sh`、`wsl-second-node.sh`、
> `wsl-fix-networking.sh` 三个更细分的工具脚本，需要单独排查时用）。

### 10.5 手工分步版（等价路径）

如果想手动逐步来，或脚本某一步出错需要单独定位：

**第一步：装第二发行版**（Windows PowerShell）

```powershell
wsl --install -d Ubuntu-24.04
```

验证：

```powershell
wsl -l -v
```

应该能看到 `Ubuntu` 和 `Ubuntu-24.04` 两个发行版都在 Running 状态。

> **如果新发行版的 IP 不是 `172.18.x.x`**（比如显示 `10.10.10.2` 或 `172.16.x.x`），
> 说明它和 Jenkins 发行版的网络模式不一致，**先做 10.2.1 的网络模式统一**，
> 否则后面 SSH 一定连不上。脚本 `wsl-setup-all.sh` 会在阶段 1 自动检测并处理。

**第二步：连通性诊断**（可选但推荐）

```bash
bash deploy/wsl-net-probe.sh Ubuntu-24.04
```

它会一次性告诉你：本机与目标的 IP、是否同网段、sshd 状态、22 端口是否可达，
并给出对应的解决方案。排查问题时先跑它，比盲猜快得多。

**第三步：准备第二节点**

```bash
cd /mnt/i/练习/nginx
bash deploy/wsl-second-node.sh --distro Ubuntu-24.04
```

这个脚本会跨发行版自动完成 4 件事：

| 步骤 | 动作 | 解决的坑 |
|---|---|---|
| 1 | 在目标发行版写 `/etc/wsl.conf` 的 `systemd=true`，然后 terminate + 重启 | 坑 ① |
| 2 | 装 `openssh-server`，配 `PasswordAuthentication no` / `PubkeyAuthentication yes`，`systemctl enable ssh` | 坑 ② |
| 3 | 生成 `/var/lib/jenkins/.ssh/deploy_key`，把公钥写进目标机 `deploy` 用户的 `authorized_keys` | SSH 免密 |
| 4 | 通过 stdin 把 `target-prepare.sh` 送进目标发行版执行（装 node/nginx/rsync、建用户目录、生成 systemd unit、nginx 配置、受限 sudoers） | 环境一致 |

> 第 4 步为什么用 stdin 而不是拷贝文件？
> 因为 WSL 发行版之间虽然共享 `/mnt/c`、`/mnt/i` 挂载，但路径里的中文（`/mnt/i/练习/nginx`）
> 和符号链接在跨发行版时容易出幺蛾子。用 stdin 管道最干净——`cat script.sh | wsl.exe -d X -u root -- bash -s`。

执行完会输出目标机 IP、部署目录、以及下一步该写什么 inventory。

### 10.6 第三步：配置 inventory（脚本已自动写入）

编辑 `deploy/inventory.ini`：

```ini
[Ubuntu-24.04]
host        = wsl:Ubuntu-24.04
ssh_user    = deploy
deploy_dir  = /srv/nginx-project
run_user    = appuser
role        = full
health_port = 80
enabled     = true
```

注意 `host` 写的是 `wsl:Ubuntu-24.04` 而不是 IP。

### 10.7 第四步：验证并部署

先手工验证 SSH 链路通不通：

```bash
sudo -u jenkins ssh -i /var/lib/jenkins/.ssh/deploy_key \
    -o StrictHostKeyChecking=no deploy@<上一步输出的IP> "hostname; whoami"
```

应输出目标机主机名和 `deploy`。

再演练（不改任何文件）：

```bash
sudo -u jenkins bash deploy/remote-deploy.sh \
    /var/lib/jenkins/workspace/nginx-deploy \
    deploy/inventory.ini Ubuntu-24.04 --dry-run
```

日志里应能看到：

```
[DRY_RUN] 解析主机 wsl:Ubuntu-24.04 -> 172.18.45.23
[DRY_RUN] rsync -> deploy@172.18.45.23:/srv/nginx-project/{backend,frontend}
```

正式部署，在 Jenkins 页面勾选 `REMOTE_DEPLOY` 后构建。

### 10.8 从浏览器访问「目标机」的网站

这是 WSL 模拟和真实服务器最大的不同：**目标机在同一个 Windows 机器内**。

三种方式：

**方式 A：直连目标机的 WSL IP**（最简单）

```powershell
wsl -d Ubuntu-24.04 -- hostname -I
# 浏览器打开 http://<那个IP>/
```

> 注意：因为 `localhostForwarding=true`，Windows 的 `localhost` 会被**第一个**占用该端口的发行版接管。
> 两个发行版都跑 nginx:80 时，`http://localhost` 只会走到其中一个——这是 WSL 的已知行为，不是配置错误。
> 所以务必用**目标机的 WSL IP** 访问，别用 localhost。

**方式 B：给目标机单独开一条 ngrok 隧道**

ngrok 免费版同时只能开 **1 条** 隧道，你现在这条已经被 Jenkins 的 8080 占了。所以要开第二条得：

```powershell
# 先停掉当前隧道
ngrok http 8080 --log stdout
```

或者用 ngrok 的配置文件管理多隧道（免费版仍限 1 个 agent session）。**不推荐**，性价比低。

**方式 C：改目标机 nginx 监听端口**

让目标机监听 8081，避免与本机 80 端口抢：

```bash
# 在目标发行版内
sudo sed -i 's/listen 80;/listen 8081;/' /etc/nginx/sites-available/nginx-app
sudo nginx -t && sudo systemctl reload nginx
```

同时把 inventory 的 `health_port` 改成 `8081`。这样 Windows 侧 `http://localhost:8081` 就能明确命中目标机。

### 10.9 WSL 模拟环境的已知差异

用 WSL 模拟真实服务器时，以下行为与真机不同，**心里有数即可，不必修**：

| 差异 | 说明 |
|---|---|
| 延迟极低 | 真实服务器有网络延迟，rsync 耗时、连接超时都不会触发；WSL 里几乎瞬时 |
| 端口冲突 | 真机上各机独立无冲突，WSL 里两个发行版共享 Windows 的 `localhost` 转发 |
| IP 动态 | 真机 IP 固定，WSL 每次重启都变（这也是为什么必须用 `wsl:` 语法） |
| systemd 生命周期 | WSL 发行版「没人用」时会自动挂起，真机是 7×24 常驻。WSL 里目标机服务可能随发行版休眠而停 |
| 无防火墙 | 真机有 ufw/firewalld，WSL 默认没有，所以「防火墙放行 22」这一步不用做 |
| 无真实网卡 | 真实带宽、丢包、延迟抖动都测不出来 |

> **休眠这一条最容易被忽略**：如果目标发行版因为长时间无 SSH 连接被 WSL 挂起，
> 下次 Jenkins 连过去时，WSL 会自动唤醒它，但 systemd 里的服务需要重新拉起，
> 可能出现「连上了但 4001/4002 没监听」。解决办法：
> 在目标发行版内执行 `sudo systemctl enable ssh`（脚本已做），
> 并保持发行版处于 Running 状态（`wsl -d Ubuntu-24.04 -- echo keepalive`）。

## 11. 常用排障命令

```bash
# 手动执行一次部署并看完整日志
sudo -u jenkins bash -x deploy/remote-deploy.sh \
    /var/lib/jenkins/workspace/nginx-deploy deploy/inventory.ini web-01

# 只测 SSH 链路
ssh -i /var/lib/jenkins/.ssh/deploy_key deploy@192.168.1.101 "systemctl is-active api-server1"

# 看远端服务日志
ssh -i /var/lib/jenkins/.ssh/deploy_key deploy@192.168.1.101 \
    "sudo journalctl -u api-server1 -n 50 --no-pager"

# 看远端 nginx 错误
ssh -i /var/lib/jenkins/.ssh/deploy_key deploy@192.168.1.101 \
    "sudo tail -n 50 /var/log/nginx/error.log"

# 检查 sudo 白名单是否生效
ssh -i /var/lib/jenkins/.ssh/deploy_key deploy@192.168.1.101 \
    "sudo -n systemctl restart api-server1 && echo 白名单OK"
```

| 现象 | 排查方向 |
|---|---|
| `SSH 不通` | 22 端口、防火墙、`BatchMode=yes` 禁用了交互式密码输入所以必须免密 |
| `Permission denied (publickey)` | 私钥权限/属主、`authorized_keys` 权限/属主、`sshd_config` 里 `PubkeyAuthentication` |
| `sudo: a password is required` | 白名单命令路径与实际不符（必须写完整绝对路径），或 sudoers 文件权限不是 440 |
| `rsync: change_dir ... failed` | `deploy` 用户对 `deploy_dir` 无写权限，重跑 `target-prepare.sh` |
| `unit 的 WorkingDirectory 与 ... 不一致` | inventory 的 `deploy_dir` 与目标机 unit 不一致 |
| 健康检查 404 | nginx `root` 路径错，或 `version.json` 被 `--delete` 删了（脚本已用模板兜底） |
| 部署成功但版本面板是 `v1.0.0-dev` | 阶段 4 没跑（直接跑了 remote-deploy.sh），或走了 DRY_RUN |

### WSL 模拟环境专属故障

| 现象 | 根因 | 处理 |
|---|---|---|
| `Connection refused` / SSH 连不上 | 目标发行版没装 sshd，或没 `systemctl enable ssh` | 跑 `wsl-second-node.sh` 第 2 步 |
| 连上了但 `systemctl` 报错 | 目标发行版没开 systemd | 写 `/etc/wsl.conf` 的 `[boot] systemd=true`，然后 `wsl --terminate <发行版>` |
| 昨天能连今天不能连 | inventory 写死了 IP，WSL 重启后 IP 变了 | 改成 `host = wsl:<发行版名>`，让脚本动态解析 |
| 浏览器打开 `localhost` 看到的是本机不是目标机 | 两个发行版都占 80 端口，Windows 只转发给一个 | 用目标机的 WSL IP 访问，或给目标机换端口（如 8081） |
| 部署时 `rsync` 报 `change_dir failed` | `deploy` 用户对 `deploy_dir` 无写权限 | 重跑 `wsl-second-node.sh`（会重跑 target-prepare.sh） |
| 连上了但 4001/4002 不通 | 目标发行版被 WSL 挂起，systemd 服务已停 | `wsl -d <发行版> -- echo keepalive` 唤醒，再 `systemctl restart api-server1 api-server2` |
| `wsl.exe --status` 返回非零 | 在沙箱/受限环境里执行 | 忽略，只要 `wsl.exe -d <发行版> -- echo ok` 能通即可 |
| **SSH 一直超时 / ping 不通** | **两发行版跨网段**（本机 172.18.x.x，目标 10.x 或 172.16.x.x） | 跑 `bash deploy/wsl-fix-networking.sh` 统一为 `networkingMode=nat`，然后在 Windows 执行 `wsl --shutdown` |
| 改了 `.wslconfig` 但 IP 没变 | 没执行 `wsl --shutdown`，或只重启了一个发行版 | 必须 `wsl --shutdown` 一次性关掉所有发行版再重进 |
| `wsl --shutdown` 后 Jenkins 也停了 | Jenkins 跑在 WSL 里，shutdown 会一起停 | 重进 Jenkins 发行版，`systemctl status jenkins` 确认自动拉起；`systemctl enable jenkins` 保证开机自启 |
